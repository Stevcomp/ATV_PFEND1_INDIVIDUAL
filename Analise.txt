ANÁLISE DO PROJETO — DEVRESOURCES MANAGER

1. OBJETIVO DO SISTEMA

O DevResources Manager é um catálogo local para registrar e consultar ferramentas úteis para desenvolvimento web. Cada registro contém nome, categoria, tipo, descrição e link. O usuário pode listar, buscar, cadastrar, editar e excluir ferramentas.

O front-end foi desenvolvido com Next.js, React e Bootstrap. O back-end usa Node.js e Express. A API mantém os registros em um array na memória do processo: eles ficam disponíveis enquanto o servidor está ligado e são apagados quando o back-end reinicia.

2. VISÃO GERAL: COMO AS PARTES SE CONECTAM

O navegador exibe as páginas do Next.js. As páginas e componentes React cuidam da interface e enviam pedidos HTTP usando fetch. Esses pedidos chegam à API Express. No back-end, o caminho é:

Navegador → página do Next.js → fetch → rota Express → controller → service → model → array em memória

A resposta volta pelo caminho inverso. A página recebe os dados em JSON, atualiza o estado do React e a interface é redesenhada.

O front-end não lê nem altera diretamente o array do back-end. Toda consulta ou mudança passa pelas rotas da API. Isso separa a interface das regras de validação e do armazenamento.

3. PÁGINAS DO FRONT-END E SUAS ROTAS

O Next.js usa a estrutura de pastas dentro de frontend/src/app para definir os endereços das páginas:

- frontend/src/app/page.jsx → endereço /: página inicial e catálogo.
- frontend/src/app/ferramentas/nova/page.jsx → endereço /ferramentas/nova: cadastro.
- frontend/src/app/ferramentas/editar/[id]/page.jsx → endereço /ferramentas/editar/ID: edição de um registro específico. [id] é um segmento dinâmico; por exemplo, /ferramentas/editar/3 passa o valor 3 à página.

Todas as páginas são envolvidas por frontend/src/app/layout.jsx. Por isso compartilham o cabeçalho, o rodapé, o Bootstrap e os estilos globais.

3.1. Layout compartilhado — layout.jsx

O layout é a estrutura comum das páginas. Importa o CSS do Bootstrap e globals.css, exibe o componente Header, coloca a página atual dentro de main e mostra o rodapé. Também define os metadados do site e o idioma pt-BR.

O layout não controla o cadastro nem consulta a API; ele apenas fornece a moldura comum da interface.

3.2. Cabeçalho — components/Header/index.jsx

O Header aparece no layout e, portanto, em todas as páginas. O nome DevResources Manager é um link para /. O link GitHub abre o repositório do projeto em outra aba. Esse componente é reutilizável; alterar seu conteúdo muda o cabeçalho de todas as páginas.

A página inicial também tem seu próprio botão “Cadastrar ferramenta”, que leva a /ferramentas/nova. Esse botão é separado do link GitHub do cabeçalho.

3.3. Página inicial — app/page.jsx

A página inicial é o catálogo. Quando abre, usa useEffect para:

1. Ler o parâmetro mensagem da URL. Se ele for cadastrada ou atualizada, mostra uma confirmação correspondente.
2. Remover o parâmetro da barra de endereço com history.replaceState.
3. Fazer GET /api/ferramentas para obter a lista da API.

useState guarda a lista de ferramentas, o texto da busca, o estado de carregamento, uma mensagem de erro e uma confirmação de sucesso. Quando algum estado muda, React atualiza a parte necessária da tela.

A busca é local: não envia outro pedido à API. Para cada registro, combina nome, categoria, tipo e descrição e verifica se o texto contém o termo digitado, ignorando maiúsculas e minúsculas e espaços no começo ou no fim da busca.

Quando há resultados, a página cria um CardFerramenta para cada registro. Se a API falhar, mostra o erro e não apresenta a falha como se o catálogo estivesse vazio. Se a busca não encontrar resultados, ou se a lista estiver vazia, mostra a mensagem apropriada.

A página também define excluirFerramenta(id), que é passada aos cartões. Depois de pedir confirmação ao usuário, a função faz DELETE /api/ferramentas/ID. Se a API confirmar, remove o cartão do estado local e mostra uma mensagem de sucesso. Se falhar, mostra um erro.

3.4. Cadastro — app/ferramentas/nova/page.jsx

A página de cadastro monta o título, uma instrução e o componente compartilhado FormFerramenta. Passa duas propriedades ao formulário:

- onSubmit={salvar}: a função que receberá os dados preenchidos.
- textoBotao="Cadastrar": o texto do botão principal.

Quando o formulário chama salvar(dados), a página faz POST /api/ferramentas. O cabeçalho Content-Type informa que o corpo está em JSON; JSON.stringify converte o objeto JavaScript em texto JSON. Se a API responder com sucesso, useRouter navega para /?mensagem=cadastrada. A página inicial lê esse parâmetro, mostra a confirmação e carrega novamente o catálogo.

3.5. Edição — app/ferramentas/editar/[id]/page.jsx

O [id] na pasta torna a rota dinâmica. useParams lê o ID do endereço, por exemplo, 3 em /ferramentas/editar/3. Esse ID permite à página pedir à API o registro correto; ele ainda precisa buscar os outros campos.

Ao abrir a página, useEffect chama GET /api/ferramentas/ID. Enquanto aguarda, o estado carregando mantém a mensagem “Carregando ferramenta...” visível. O estado ferramenta começa como null porque os dados ainda não chegaram; quando a API responde, setFerramenta guarda o registro. Se a busca falhar, erro guarda a mensagem e, ao terminar a busca, a página oferece um link de volta ao catálogo.

Quando ferramenta está disponível, a página mostra FormFerramenta com valores={ferramenta}, preenchendo os campos com os dados atuais. key={ferramenta.id} permite ao React identificar o formulário daquele registro.

Ao enviar, salvar(dados) faz PUT /api/ferramentas/ID com os novos dados em JSON. Se a API confirmar a atualização, a página navega para /?mensagem=atualizada. A página inicial mostra a confirmação e consulta a lista novamente.

4. COMPONENTES COMPARTILHADOS

4.1. FormFerramenta — components/FormFerramenta/index.jsx

Esse formulário é usado tanto pela página de cadastro quanto pela página de edição. Ele contém nome, categoria, tipo, link e descrição. Nome, categoria, link e descrição são obrigatórios; tipo é opcional. Os atributos required, type="url" e maxLength oferecem validações básicas no navegador. A API também valida os dados, portanto a validação importante não depende apenas do navegador.

A propriedade valores permite iniciar o formulário com dados existentes; sem ela, os campos começam vazios. O estado form guarda o que está digitado. A função alterar usa o name de cada campo para atualizar somente a propriedade correspondente.

Ao enviar, a função enviar impede o recarregamento padrão, limpa a mensagem anterior, desativa temporariamente o botão e chama a função recebida em onSubmit. A página que utiliza o formulário decide qual operação fazer: POST no cadastro ou PUT na edição. Se houver erro, o formulário mostra a mensagem e libera o botão para uma nova tentativa. Cancelar leva ao catálogo sem enviar os dados.

O arquivo também define API_BASE e API_FERRAMENTAS. API_BASE usa NEXT_PUBLIC_API_URL quando configurada e, caso contrário, http://localhost:3001/api. API_FERRAMENTAS acrescenta /ferramentas. O arquivo exporta chamarApi, utilitário compartilhado que executa fetch, lê respostas JSON e transforma respostas HTTP malsucedidas em erros para as páginas ou o formulário tratarem.

4.2. CardFerramenta — components/CardFerramenta/index.jsx

O cartão apresenta categoria, nome, tipo (se houver), descrição e link externo. O botão Editar abre /ferramentas/editar/ID. O botão Excluir chama a função onExcluir recebida da página inicial e passa o ID da ferramenta.

O cartão não exclui o registro sozinho: a página inicial controla a confirmação, a chamada à API e a atualização da lista. Esse desenho mantém a responsabilidade da operação no componente que controla o catálogo.

5. COMO A API DO BACK-END É ORGANIZADA

5.1. Inicialização: server.js e config/ambiente.js

backend/server.js é o ponto de entrada dos comandos npm start e npm run dev. Ele carrega a configuração da porta e inicia o servidor Express usando o app configurado em app.js. backend/config/ambiente.js lê o arquivo de ambiente quando indicado, usa 3001 como padrão e valida a porta.

5.2. Configuração: app.js

backend/app.js cria a aplicação Express, configura a leitura de corpos JSON e os cabeçalhos CORS usados pelo navegador. Também registra GET /api/check, conecta as rotas em /api/ferramentas e define respostas para caminhos inexistentes e erros internos.

O arquivo instancia as camadas e injeta cada dependência na camada que a utiliza: o service recebe o model; o controller recebe o service; e as rotas recebem o controller.

5.3. Rotas: routes/ferramentaRoutes.js

As rotas associam método e endereço HTTP às funções do controller. Elas definem por onde os pedidos entram, sem concentrar a validação ou o armazenamento.

5.4. Controller: controllers/FerramentaController.js

O controller recebe os dados da requisição HTTP, chama a operação correspondente do service e transforma o resultado em resposta HTTP com JSON e status apropriados. Erros conhecidos, como dados ou IDs inválidos e registro inexistente, viram respostas 400 ou 404. Outros erros seguem para o middleware central do app.js.

5.5. Service: services/FerramentaService.js

O service contém as regras das operações. Converte e valida IDs, cria uma instância de Ferramenta para validar os dados e pede ao model para consultar, criar, atualizar ou excluir. Se o registro não existir, informa o erro para o controller responder com 404.

5.6. Modelo de validação: models/Ferramenta.js

A classe Ferramenta verifica os campos antes de permitir o armazenamento: nome, categoria, descrição e link são obrigatórios; tipo é opcional; há limites de tamanho; e o link deve ser uma URL HTTP ou HTTPS. Os textos são aparados nas extremidades. O ID é incluído quando a instância representa uma atualização.

5.7. Armazenamento: models/FerramentaModel.js

O model mantém os registros em um array e atribui IDs numéricos crescentes. Implementa listagem, busca por ID, criação, atualização e exclusão. Retorna cópias dos registros para que quem recebe os dados não altere diretamente o array. Como o array existe apenas na memória, reiniciar o servidor apaga os dados.

6. ROTAS DA API E OPERAÇÕES

- GET /api/check — verifica se a API está respondendo.
- GET /api/ferramentas — retorna todas as ferramentas.
- GET /api/ferramentas/:id — retorna uma ferramenta específica.
- POST /api/ferramentas — valida e cria uma ferramenta.
- PUT /api/ferramentas/:id — valida e substitui os dados da ferramenta indicada.
- DELETE /api/ferramentas/:id — remove a ferramenta indicada.

POST é usado para criar; PUT é usado para atualizar um registro identificado pelo ID. Os pedidos e respostas de dados usam JSON.

7. FLUXOS COMPLETOS ENTRE AS PÁGINAS

CADASTRO

1. O usuário abre /ferramentas/nova pelo botão de cadastro da página inicial.
2. A página exibe FormFerramenta vazio e passa a função salvar.
3. O formulário coleta e valida os campos no navegador; ao enviar, chama salvar(dados).
4. A página envia POST /api/ferramentas.
5. A rota encaminha ao controller, que chama o service.
6. O service valida os dados com Ferramenta e pede ao model para armazená-los.
7. O model cria o ID e guarda o registro em memória.
8. A API retorna sucesso; o front-end volta para /?mensagem=cadastrada.
9. A página inicial mostra a confirmação, busca a lista e apresenta o novo cartão.

EDIÇÃO

1. O usuário clica em Editar no cartão e abre /ferramentas/editar/ID.
2. A página obtém o ID com useParams e faz GET /api/ferramentas/ID.
3. A API consulta o model; a página recebe o registro e preenche FormFerramenta.
4. Ao salvar, o formulário chama a função salvar da página de edição.
5. A página envia PUT /api/ferramentas/ID; a API valida e atualiza o registro.
6. O front-end volta para /?mensagem=atualizada.
7. A página inicial mostra a confirmação e carrega os dados atualizados.

EXCLUSÃO

1. O usuário clica em Excluir no cartão.
2. O cartão chama onExcluir(ID), função que a página inicial passou como propriedade.
3. A página pede confirmação e, se o usuário confirmar, envia DELETE /api/ferramentas/ID.
4. A API remove o registro do model e responde.
5. A página retira o cartão do estado local e mostra a confirmação; não precisa carregar a página inteira novamente.

8. ERROS E VALIDAÇÃO

O navegador aplica validações básicas dos campos. O back-end repete validações importantes porque os pedidos à API poderiam vir de outros clientes e não apenas desse formulário.

chamarApi verifica se a resposta é JSON, lê seu conteúdo e verifica o status HTTP. Uma resposta de erro vira uma exceção que pode ser tratada pela página ou pelo formulário. A tela de edição diferencia registro inexistente (404) de falhas de conexão. No catálogo e no formulário, erros são apresentados ao usuário.

9. CONFIGURAÇÃO E EXECUÇÃO LOCAL

O endereço padrão da API é http://localhost:3001/api. O front-end aceita NEXT_PUBLIC_API_URL para apontar a outro endereço. O Next.js é executado normalmente em http://localhost:3000.

Para iniciar o back-end, abra um terminal na pasta backend, instale as dependências com npm ci e execute npm run dev. Em outro terminal, abra frontend, execute npm ci e npm run dev. Acesse http://localhost:3000 no navegador. GET http://localhost:3001/api/check pode confirmar se a API está ativa.

11. LIMITES ATUAIS DO SISTEMA

- Os dados são temporários e desaparecem quando o back-end reinicia, pois não há banco de dados.
- A busca acontece no navegador e abrange nome, categoria, tipo e descrição.
- O sistema não exige login nem separa dados por usuário.
- O link da ferramenta é validado como URL HTTP ou HTTPS, mas não há verificação de duplicidade: o mesmo link pode ser cadastrado mais de uma vez.
- O link GitHub no cabeçalho abre o repositório configurado no componente Header; para que visitantes possam acessá-lo, o repositório precisa ser público.
